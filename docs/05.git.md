# 5. Git

[git - official documentation](https://git-scm.com/)

[git](https://en.wikipedia.org/wiki/Git) is a distributed version control system
originally created by Linus Torvalds for administering the code for the Linux
kernel.

It is a great way to keep your source files in order!

Every change in your code can be stored using git as a separate diff.
Also, you can have paralell versions of your code available from the same
directory.

## Installing git on your client computer

Windows (need to refresh PATH before git works):
```
winget install Git.Git
```

OSX: [install MAC](https://git-scm.com/install/mac)

## Initial configuration

Git puts your name on every commit, so tell it who you are:

```console
$ git config --global user.name "Anna Andersson"
$ git config --global user.email "anna@example.org"
```

## Starting a repo

Either turn an existing directory into one:

```console
$ cd ~/projects/analysis
$ git init
```

The result is that a new directory was created, named `.git`.
All git files will reside in that directory.
If you want to remove the `git` part, you simply remove `.git`.

or take a copy of one that already exists:

```console
$ git clone git@github.com:anna/analysis.git
$ cd analysis
```

## The everyday loop

```console
$ git status                    # what has changed - use this constantly
$ git add script.py             # stage a file for the next commit
$ git add .                     # stage everything changed here
$ git commit -m "Fix off-by-one in the window size"
$ git log                       # show commit history, "Q" to quit
$ git log --oneline             # the history, one line per commit
$ git diff                      # what has changed since last commit
```

`git status` is the command you run when you are not sure what is going on.
It usually also suggests what to type next.

Working with a remote:

```console
$ git push          # send your commits to remote (could be GitHub)
$ git pull          # fetch and apply commits from remote
```

## What not to commit

Commit the things you write. Do not commit things that can be regenerated,
things that are large, and things that are secret:

- data sets and model checkpoints — Git stores every version forever, and a
  repo with a 2 GB file in its history stays 2 GB even after you delete it
- results, figures and logs that a script produces
- virtual environments (`.venv/`, `__pycache__/`)
- passwords, API keys, tokens

List them in a file called `.gitignore` in the top of the repo:

```
.venv/
__pycache__/
results/
*.log
```

`.gitignore` itself *should* be committed. Small input files are fine to
commit — this repo tracks `data/sample.txt` on purpose — but a corpus or a
model checkpoint is not.

If a secret does get committed, deleting it in a later commit is not enough —
it is still in the history. Change the password.


## Staging vs committing

Nothing is recorded until you commit. `git add` decides *what goes into* the
next commit, which is how you commit one change at a time even when you have
edited several files.

```
   your files          staged             history
  (edit freely)  ->   (git add)   ->   (git commit)
```

## Git commit messages

This is the message that shows in the commit log (`git log`).
The quick way to add a message is to have it a part of the command:

```console
git commit -m "this is my message"
```

But, if you want to manually edit a longer message, you can do `git commit`
without the `-m` option. This will open a text editor as part of the commit
procedure. The choice of text editor is determined by a git configuration.

### Default text editor for git commits

A common default is the CLI text editor `vim`. It is not very intuitive
to use. You can configure git to use another editor.
For example Visual Studio Code:

```console
git config --global core.editor "code --wait"
```

*Some text editors need a special option so that they open the git message properly.*

## Comparing and viewing code changes with git diff

If you have uncommitted changes, you can view the diff using (`Q` to quit):
```console
git diff
```

You can do a diff comparing a separate branch, or a specific commit
```
git diff some-feature                   # a branch
git diff 77dddf35fbaa1243a7b49add655e8209ac6b99cc     # a commmit
```

## Remotes

You can have several remote git repositories. Check which ones you have:

```console
git remote -v
```

`origin` is the default name for the remote from which you cloned.
It is also common when creating your first remote manually.

You can manually add a remote and name it:

```console
git remote add newname git@github.com:someone/something.git
```

Pushing to the git remote for the first time:

```console
git push -u newname main
```

## Branches

Creating a new branch is like creating a copy of the current repository, but
no files are added. Branches are useful when you want to develop new features
and don't want to mess up the main branch.

Check which branch is currently active:

```console
git branch
```

You can create new branches based on the branch you are currently using and
give it any name you want:

```console
git branch some-feature
git checkout some-feature
```

Or, in a single line:
```console
git checkout -b some-feature
```

Push and pull the new branch

```console
git push newname some-feature
git pull newname some-feature
```

## Git merge

If you did development on a separate branch and want to add those commits
to the main branch you can do a `git merge`. This is where things can get a
little bit tricky. If both branches have diverging additional commits there may
be conflicts, which need to be sorted out manually.

A typical work flow:
```console
git branch                  # check which branch you are on
git checkout main           # change to main where you will do the merge
git merge some-feature      # merge `main` with `some-feature`
```

### When you have merge conflicts

Git stops and tells you which files it could not merge on its own:

```console
git status
```

Open each one. The conflicting part is marked, your version first:

```
<<<<<<< HEAD (Current Change)
window_size = 10
=======
window_size = 25
>>>>>>> some-feature (Incoming Change)
```

Edit it into what it should be and delete the three marker lines. For example:

```
window_size = 25
```

Then:

```console
git add script.py
git commit
```

If you would rather not deal with it now, undo the whole merge:

```console
git merge --abort
```

Nothing is lost, and you are back where you were before the merge.

### Cleanup

if all went well, delete the extra branch:

```console
git branch -d some-feature
```

Note that `git pull` is essentially a merge. It pulls changes from a remote branch
and applies them.

## Git config

Git has configuration files in two places. A global configuration file in
your home directory, and another in the repository you are using.

A git configuration is never pushed with the repository. It is specific to
the copy of the repository you are managing locally.

To see your global git config:

(on Mac/Linux "dotfiles" are hidden files):
```
cat ~/.gitconfig
```

The git configuration for a repository lives in `.git/config` at the root
of the repository.
