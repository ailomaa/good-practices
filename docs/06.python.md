# 6. Python

## Running Python

Plain `python` may be missing on some systems, in which case you need to use
`python3`.

```console
$ python3 script.py          # run a script
$ python3                    # interactive prompt - exit() or Ctrl+D to leave
$ python3 -c "print(2+2)"    # run one line
```

## Versions

A machine usually has several Pythons installed at once, and they are not
interchangeable — packages installed for one are invisible to another.

```console
$ python3 --version
Python 3.12.3
$ which python3
/usr/bin/python3
```

Servers often keep more than one available:

```console
$ ls /usr/bin/python3*
/usr/bin/python3  /usr/bin/python3.11  /usr/bin/python3.12
```

You can ask for a specific one by name: `python3.11 script.py`.

## Virtual environments (venv)

A virtual environment is a directory containing its own copy of Python and its
own packages. One per project. It is the standard tool, included with Python,
and it is what you should reach for by default.

```console
$ cd ~/projects/analysis
$ python3 -m venv my-venv        # create it - once per project
$ source my-venv/bin/activate    # switch into it - once per terminal
(my-venv) $ pip install pandas
(my-venv) $ python3 script.py
(my-venv) $ deactivate           # leave it
$ rm -rf my-venv                 # remove the venv
```

Note the prompt: it gains a `(my-venv)` prefix while the environment is active.
That prefix is the whole point — it tells you which Python you are about to
run.

Record what you installed so the server can reproduce it:

```console
(my-venv) $ pip freeze > requirements.txt
```

and on the other machine:

```console
anna@server:~$ python3 -m venv my-venv
anna@server:~$ source my-venv/bin/activate
(my-venv) anna@server:~$ pip install -r requirements.txt
```

## Conda

Conda does the same job as `venv` and `pip` together, and more: it can install non-Python software (CUDA,
compilers, R) and it can install *different versions of Python itself*. On
HPC systems it is often what everyone uses.

Example where we specify a python version for the conda env:
```console
$ conda create -n analysis python=3.11
$ conda activate analysis
(analysis) $ conda install pandas
(analysis) $ conda deactivate
```

Export and recreate:
```console
(analysis) $ conda env export > environment.yml
$ conda env create -f environment.yml
```

Which to use: `venv` if your dependencies are pure Python, which covers most
work. Conda if you need a Python version the machine does not have, or
packages that are not really Python.

***Do not use both at once. A conda environment with a venv activated inside it
is a reliable way to spend an afternoon confused.***

## Which Python am I actually using?

This is the question behind most "but it works on my laptop" problems. Four
ways to answer it, in increasing order of trustworthiness:

```console
$ echo $VIRTUAL_ENV       # path to the active venv, empty if none
$ conda env list          # * marks the active conda environment
$ which python3           # which program the shell will run
$ python3 -c "import sys; print(sys.executable)"
/home/anna/projects/analysis/my-venv/bin/python3
```

The last one asks Python itself, and is the one to use when the answer
surprises you. To see where a package came from:

```console
$ pip -V
pip 24.0 from /home/anna/projects/analysis/my-venv/lib/python3.12/site-packages/pip
```

If that path is not inside your environment, `pip install` is putting packages
somewhere you did not intend. Using `python3 -m pip install` instead of plain
`pip` avoids this: it installs into the same Python you are running.
